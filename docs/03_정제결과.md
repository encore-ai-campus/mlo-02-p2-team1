# 데이터 정제와 정제 후 데이터

[README.md](../README.md)의 「정제 후 데이터」 상세입니다. 실행 옵션과 출력 형식은 [pipeline/README.md](../pipeline/README.md)에 있습니다.

## 1. 처리 흐름

```mermaid
flowchart TD
    A[오염 CSV 6종 · 폴더 또는 ZIP] --> B[Bronze: 원본 보존 · 체크섬 · 명세 검증]
    B --> C[진단코드 기반 탐지 · 근거 기반 복구]
    C --> D[복구 결과 전체 행 · 관리 컬럼]
    C --> E[격리 대상 행 별도 출력]
    D --> F[동일 규칙 재검사 · 품질 리포트]
    D --> G[정제 후 검증]
    H[추가 데이터 5종] --> G
    G --> I[MySQL 스테이징 · 정규화 적재]
```

### ① 원본 보존과 구조 검증

입력은 [배포 폴더](../data/01_raw/F1_distribution.zip) 또는 같은 구성의 ZIP입니다. `all_years/` 아래 CSV 6종을 문자열로 읽고 원본 파일은 수정하지 않습니다. 파일별 행·컬럼 수, 컬럼 구성·순서, SHA-256 체크섬을 명세서와 배포 체크섬에 대조해 `bronze_manifest.csv`에 기록합니다.

### ② 진단과 근거 기반 복구

[pipeline/recovery.py](../pipeline/recovery.py)가 결측·형식·키·관계·시간·구간 규칙을 검사하고 근거가 충분한 값만 수정합니다.

| 대상 | 복구 근거·방법 |
|---|---|
| 대회 식별자 | 같은 세션의 하위 5개 파일이 가리키는 합의값 |
| 드라이버 신원·팀 | 시즌 내 차량번호별 신원 합의값, 앞뒤 세션 소속팀과 팀 색상 |
| 국가 코드·프로필 URL | 같은 드라이버의 다른 세션 기록, 같은 시즌의 유일한 URL |
| 섹터 시간 | 한 섹터만 비었을 때 `랩타임 - 나머지 두 섹터 시간` |
| 랩타임·시작 시각 | 인접 랩의 시각 차이, 시각 교환·랩 기록 전체 교환·시간 연속성 |
| 타이어·스틴트 | 컴파운드 결측은 `UNKNOWN`, 경계는 인접 스틴트·랩 기록 |
| 기상 측정값 | 단일 튐값의 앞뒤 측정값 평균 |

중앙값 등으로 결측을 일괄 채우지 않습니다. 근거가 부족하면 `OPEN`, 원천 특성으로 허용하면 `ACCEPTED`, 복구가 끝나면 `REPAIRED`로 기록합니다. 분석을 왜곡할 수 있는 미해결 결함은 `quarantine_flag=Y`로 표시합니다.

### ③ 파일 판정: PASS · REVIEW · FAIL

| 판정 | 조건 | 실행 결과 |
|---|---|---|
| FAIL | 원본 체크섬·명세 불일치, 또는 복구·허용·격리되지 않은 **ERROR 등급** 결함이 남음 | 리포트를 모두 쓴 뒤 종료 코드 1 (관리자 페이지 실행은 여기서 멈춤) |
| REVIEW | 그 밖의 미해결(`OPEN`) 결함이 남음 | 정상 종료, 검토 대상 |
| PASS | 미해결 결함 없음 | 정상 종료 |

판정과 사유는 `repair_summary.csv`의 `status`·`fail_reason`, 실행 전체 판정은 `run_result.json`의 `status`·`fail_files`에 남습니다.

### ④ 복구 이력·격리·재검증

`repaired/`에는 **격리 행을 포함한 전체 행**을 저장하고 `quarantine/`에는 격리 대상 행을 별도로 저장합니다. 분석할 때에는 `quarantine_flag=Y`를 제외해야 합니다. 복구 CSV에는 `original_*`, `repair_status`, `repair_method`, `repair_confidence`, `repair_reason`, `dq_codes`, `quarantine_flag`를 남기고, 이슈와 변경 이력은 `issue_id`로 연결합니다. 복구 후 같은 규칙으로 재검사한 잔여 건수도 기록합니다.

### FAIL 정제 전후 (ERROR 등급)

ERROR 등급 결함은 남아 있으면 FAIL입니다. 정제 전에는 탐지된 ERROR가 모두 FAIL 사유이고, 정제 후에는 복구·허용·격리되지 않고 남은 ERROR만 FAIL 사유입니다. 출처: [fail_before_after.csv](../data/04_reports/quality/fail_before_after.csv).

| 데이터 | ERROR 탐지 | 복구 | 허용 | 격리 | 남음 | 정제 전 | 정제 후 | 진단코드 |
|---|---:|---:|---:|---:|---:|---|---|---|
| sessions | 2 | 2 | 0 | 0 | 0 | FAIL | PASS | DQ015 대회 식별자 불일치 |
| drivers | 24 | 24 | 0 | 0 | 0 | FAIL | REVIEW | DQ016 신원 뒤바뀜 20, DQ017 팀 불일치 4 |
| laps | 102 | 58 | 42 | 2 | 0 | FAIL | REVIEW | DQ019 랩 시작 시각 불일치 |
| stints | 11 | 0 | 11 | 0 | 0 | FAIL | REVIEW | DQ010 빈 스틴트(원천 특성) |
| weather | 0 | 0 | 0 | 0 | 0 | PASS | PASS | |
| pit | 2 | 0 | 0 | 2 | 0 | FAIL | REVIEW | DQ021 피트 시간 컬럼 충돌 |

랩 시작 시각(DQ019)은 처음 판정 규칙을 넣었을 때 47건이 남아 laps가 FAIL이었습니다. 다음 근거로 정리해 FAIL을 해소했습니다.

- **기록 전체 교환 복구:** 9912 #87의 랩 3·4는 시각·랩타임·섹터가 통째로 바뀌어 있어 서로 교환했습니다(22셀).
- **세션 공통 사건 허용:** 같은 세션·같은 랩(±1)에서 드라이버 2명 이상이 함께 어긋난 경우는 적기·체커 이후 같은 원천 특성으로 보고 허용했습니다(9496·9205 적기, 9157 체커 이후).
- **타이밍 오차 허용:** 앞 랩 기준 3초 이내 차이는 원천 타이밍 오차로 허용했습니다.
- **격리:** 단독으로 크게 어긋나고 근거가 없는 2행(9181 #11 랩 2, 11353 #41 랩 6)은 격리했습니다.

행은 삭제하지 않습니다. 따라서 `원본 유지 + 복구 + 격리 = 입력 행`이며, 이 대사는 [데이터 검증](./04_데이터검증.md)에서 다시 확인합니다.

## 3. 정제 결과에서 도출한 결론

- **세션·드라이버 연결의 신뢰도 개선:** 대회 키 2셀, 드라이버 신원 20셀, 팀명 4셀을 복구했습니다. 경기·선수·팀을 잘못 연결하는 문제를 줄였습니다.
- **랩·섹터 분석용 값 복원:** 섹터 시간 489셀, 랩타임 2셀, 시작 시각 36셀과 기록이 통째로 바뀐 랩 1쌍(22셀)을 복구했습니다. 다만 섹터 결측 1,000건과 랩타임 결측 261건 등이 미해결이므로 분석별 유효 표본을 확인해야 합니다.
- **타이어·기상 조건 정리:** 스틴트 경계 52셀, 컴파운드 7셀, 기상 측정값 5셀을 처리했습니다. 컴파운드 7셀은 실제 종류 추정이 아닌 `UNKNOWN` 표기입니다.
- **원천 결측과 복구 대상을 분리:** 속도 결측 24,101건은 대체하지 않고 허용했습니다. 속도 비교에는 측정값이 있는 표본을 사용하고 커버리지를 함께 제시해야 합니다.
- **피트·랩 분석의 왜곡 방지:** 시간 컬럼이 충돌하는 피트 2행과 근거 없이 시각이 어긋난 랩 2행을 격리했습니다. 장시간 피트 164건·정지시간 57건은 검토 대상으로 남겨 정상 피트 운영과 구분할 수 있게 했습니다.

결론적으로 **일부 연결 오류와 결측을 근거에 따라 복구했지만, 지표별로 분석에 사용할 수 있는 데이터의 범위가 다릅니다.** 후속 비교에서는 복구 건수보다 유효 표본 수, 결측 비율, 제외 기준을 함께 확인해야 합니다.
